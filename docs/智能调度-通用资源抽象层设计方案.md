# 智能调度 - 通用资源抽象层设计方案

## 1. 背景与目标

### 1.1 当前问题

当前 `inspection-task` 模块中，资源概念被硬编码为 `robot`（机器人）：

| 问题位置 | 硬编码字段 |
|---------|-----------|
| `ScheduleRuleResourcePool` | `robotPoolIds`, `robotIds` |
| `ResourcePolicy` | `preferredRobotPoolIds`, `preferredRobotIds` |
| `StructuredScheduleRule` | `fixedRobotId`, `requiredRobotCount` |
| `TaskScheduleCandidate` | `fixedRobotId`, `requiredRobotCount` |
| `InspectionTaskScheduleDO` | `assignedRobotId` |
| `InspectionTaskExecutionDO` | `robotId` |

这导致：
- 无法适配其他类型的资源（车辆、无人机、人员、设备等）
- 资源管理逻辑散落在各处，难以统一维护
- 跨项目复用困难

### 1.2 设计目标

1. **资源类型通用化**：通过 `resourceType` 区分不同资源类型（robot/vehicle/drone/person/equipment）
2. **资源管理独立化**：建立独立的资源服务层，抽象资源操作
3. **业务层解耦**：调度层只依赖资源抽象接口，不直接依赖具体资源实现
4. **可扩展性**：新项目可自行实现资源服务接口，适配不同资源

### 2.2 核心接口

#### ResourceService（资源服务接口）

```java
/**
 * 资源服务接口。
 *
 * <p>定义资源管理的通用能力，不同项目可实现此接口适配自己的资源类型。</p>
 */
public interface ResourceService {

    /**
     * 获取资源类型。
     */
    ResourceType getResourceType();

    /**
     * 根据 ID 获取资源。
     */
    Resource getById(Long id);

    /**
     * 根据 ID 列表批量获取资源。
     */
    List<Resource> getByIds(List<Long> ids);

    /**
     * 查询资源列表。
     */
    List<Resource> list(ResourceQueryDTO query);

    /**
     * 检查资源是否可用。
     */
    boolean isAvailable(Long resourceId, LocalDateTime startTime, LocalDateTime endTime);

    /**
     * 获取资源在指定时间范围内的可用时间窗口。
     */
    List<TimeWindow> getAvailableTimeWindows(Long resourceId, LocalDateTime start, LocalDateTime end);

    /**
     * 资源是否支持并行调度。
     */
    boolean supportsParallel();
}
```

## 3. 核心模型设计

### 3.1 资源类型枚举

```java
/**
 * 资源类型枚举。
 *
 * <p>定义系统支持的资源类型，每个项目可根据需要扩展。</p>
 */
@Getter
@AllArgsConstructor
public enum ResourceType {

    ROBOT("robot", "巡检机器人"),
    VEHICLE("vehicle", "车辆"),
    DRONE("drone", "无人机"),
    PERSON("person", "人员"),
    EQUIPMENT("equipment", "设备");

    /**
     * 资源类型编码。
     */
    private final String code;

    /**
     * 资源类型名称。
     */
    private final String name;

    /**
     * 根据编码获取枚举。
     */
    public static ResourceType getByCode(String code) {
        for (ResourceType type : values()) {
            if (type.getCode().equals(code)) {
                return type;
            }
        }
        return null;
    }
}
```

     * 是否允许资源切换。

     * 是否允许人工兜底。
     */
    private Boolean allowManualFallback;

    /**
     * 是否允许跨池切换。

     * 分配失败原因。

## 6. 实现策略

### 6.1 短期策略（不改核心架构）

在 `inspection-task` 模块内部建立资源抽象：

```
service/resource/
├─ api/
│   ├─ ResourceService.java
│   ├─ ResourcePoolService.java
│   └─ ResourceAllocator.java
└─ impl/
    └─ robot/
        ├─ RobotResourceServiceImpl.java
        └─ RobotResourcePoolServiceImpl.java
```

### 6.2 字段映射

| 原字段 | 新字段 | 说明 |
|-------|-------|------|
| `fixedRobotId` | `strategy.fixedResourceId` | 固定资源 ID |
| `requiredRobotCount` | `strategy.requiredCount` | 所需资源数量 |
| `robotPoolIds` | `strategy.poolIds` | 资源池 ID 列表 |
| `robotIds` | `strategy.resourceIds` | 指定资源 ID 列表 |
| `assignedRobotId` | 从 `schedule_resource` 表查询 | 已分配资源 |
| `allowResourceSwitch` | `strategy.allowSwitch` | 是否允许切换 |

### 6.3 兼容性处理

为保证向后兼容：

1. **数据库字段保留**：原有的 `assigned_robot_id` 等字段保留，作为冗余展示字段
2. **新增 `resource_type` 字段**：标识资源类型
3. **数据同步**：写入时同时写入新表和旧字段，读取时优先读新表
4. **渐进式迁移**：前端逐步切换到新接口

## 7. 迁移步骤

### 阶段一：建立抽象层（不影响现有功能）

1. 创建 `resource/api` 包，定义接口
2. 创建 `resource/model` 包，定义通用模型
3. 创建 `resource/impl/robot` 包，实现机器人资源服务
4. 添加 `resource_type` 字段到相关表

### 阶段二：调度层接入抽象

1. 修改 `TaskScheduleCandidate` 使用 `GeneralResourceStrategy`
2. 修改 `StructuredScheduleRule` 使用通用资源策略
3. 修改 `SchedulingSlotSearcher` 调用 `ResourceAllocator`
4. 修改 `ResourceConflictDetector` 使用 `ResourceService`

### 阶段三：持久化接入新表

1. 创建 `inspection_task_schedule_resource` 表
2. 修改 `TaskSchedulePersistenceService` 写入新表
3. 修改 `InspectionTaskScheduleView` 从新表查询资源

### 阶段四：清理旧字段

1. 前端切换到新接口
2. 移除冗余字段依赖
3. 保留旧字段作为历史数据

---

## 8. 总结

通过建立通用资源抽象层，实现：

1. **资源类型可扩展**：通过 `ResourceType` 枚举支持多种资源类型
2. **资源服务可替换**：通过接口抽象，不同项目可实现自己的资源服务
3. **调度层解耦**：调度引擎只依赖抽象接口，不依赖具体资源实现
4. **向后兼容**：保留旧字段和逻辑，渐进式迁移

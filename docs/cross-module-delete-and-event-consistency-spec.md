# 跨模块删除与事件一致性规范

## 1. 背景

在新的 Spring Cloud 微服务架构中，Facility、Twin、Scene、Task、Inspection、Point、Alarm 等模块需要保持业务解耦。模块间不允许再采用旧系统中“一个业务服务直接删除另一个业务模块表数据”的方式实现联动，否则会导致：

- 模块边界不清晰，形成双向依赖或隐式依赖
- 后续任务、巡检、点位等模块迁移后再次耦合
- 数据删除链路不可追踪，失败后难以修复
- 新增模块时删除逻辑持续扩散，维护成本越来越高

尤其是在 Facility 这类主业务对象被删除时，往往还需要联动清理：

- twin 映射关系
- 任务、点位、巡检配置
- 告警绑定
- 统计或索引类派生数据

这类操作一旦跨模块直接删表，会快速破坏系统解耦目标。

因此需要统一制定：

# 跨模块删除与事件一致性规范

用于约束后续所有模块的删除联动设计。

---

## 2. 目标

本规范目标如下：

1. 明确跨模块删除时的职责边界
2. 避免跨模块直接删表、直连业务实现
3. 统一删除过程中的事件模型、状态机与失败处理方式
4. 保证删除链路可重试、可观测、可恢复
5. 支撑 Facility、Area、Task、Inspection 等后续模块迁移后的统一实现方式

---

## 3. 适用范围

本规范适用于以下场景：

- 一个主业务实体删除时，需要其他模块同步清理关联数据
- 一个模块的状态变化，需要其他模块做异步收敛
- 需要通过消息总线而不是本地事务实现跨模块协同

典型对象包括但不限于：

- Facility
- Area
- Site
- Twin Mapping
- Task / Task Point
- Inspection Plan / Inspection Record
- Alarm Rule Binding
- Scene Binding / Spatial Binding

---

## 4. 基本原则

### 4.1 模块自治

每个模块只能维护并删除自己的数据表。

禁止：

- Facility 模块直接删除 Task 模块的表
- Task 模块直接删除 Twin 模块的表
- Scene 模块直接修改 Facility 模块业务状态

允许：

- 模块发布领域事件
- 模块订阅并处理自己边界内的数据
- 模块返回成功/失败回执

---

### 4.2 删除是流程，不是瞬时动作

跨模块删除不能视为一个简单的 `deleteById` 操作，而应视为一个有状态的删除流程。

因此主实体删除时：

- 先进入 `DELETING` 状态
- 再触发跨模块清理
- 全部完成后再进入 `DELETED` 状态

不允许在下游模块尚未处理完成前，直接认定删除成功。

---

### 4.3 最终一致性优先

跨模块删除默认采用：

# 最终一致性 + 状态机收敛

而不是：

# 分布式强事务回滚

原因：

- 删除动作通常不可逆
- 下游可能包含归档、索引、通知、缓存、审计等副作用
- 分布式回滚成本高且不可靠

因此系统必须优先支持：

- 幂等
- 重试
- 挂起
- 人工恢复

---

### 4.4 用户可见状态必须真实

如果删除尚未完成，前端和业务接口不能假装“已经删除成功”。

系统必须如实暴露：

- 删除中
- 部分失败
- 等待重试
- 已完成

---

## 5. 标准删除模型

### 5.1 主实体删除状态

建议主业务实体统一支持以下状态：

- `ACTIVE`：正常可用
- `DELETING`：删除流程进行中
- `DELETED`：删除完成
- `DELETE_FAILED`：删除失败且当前未自动恢复

说明：

- 若系统采用逻辑删除字段，也应保留删除流程状态字段
- `DELETING` 期间该实体默认不可继续参与新增业务操作
- 查询接口默认不返回 `DELETED` 数据

---

### 5.2 删除任务状态

建议为跨模块删除单独维护删除任务（Deletion Task），用于跟踪跨模块步骤。

推荐状态：

- `PENDING`：已创建，待分发
- `RUNNING`：下游处理中
- `PARTIAL_FAILED`：部分模块失败
- `SUCCEEDED`：所有模块完成
- `FAILED`：最终失败，需要人工介入
- `CANCELLED`：删除任务被取消

---

### 5.3 删除步骤状态

对于每个参与模块，需记录子步骤状态：

- `PENDING`
- `RUNNING`
- `SUCCEEDED`
- `FAILED`
- `SKIPPED`

例如一个 Facility 删除任务可拆分为：

- twin cleanup
- task cleanup
- inspection cleanup
- alarm cleanup
- point cleanup

---

## 6. 标准删除流程

以下流程适用于 Facility、Area 等主实体的跨模块删除。

### 6.1 发起删除请求

用户在管理端发起删除时，主模块执行：

1. 校验对象是否存在
2. 校验是否允许删除
3. 创建删除任务
4. 将主实体状态改为 `DELETING`
5. 在本地事务内写入 outbox 事件
6. 返回“删除已受理”而非“删除已彻底完成”

注意：

- 删除是否允许，需要先做本地规则校验
- 不允许未校验就直接进入删除编排

---

### 6.2 发布删除请求事件

推荐统一事件类型：

- `facility.delete.requested`
- `area.delete.requested`
- `site.delete.requested`

事件建议至少包含：

```json
{
  "eventType": "facility.delete.requested",
  "taskId": "del-20260512-0001",
  "aggregateType": "facility",
  "aggregateId": 10086,
  "operatorId": 1,
  "occurredAt": "2026-05-12T12:00:00",
  "traceId": "xxx",
  "payload": {
    "siteId": 12,
    "categoryId": 301,
    "code": "FAC-0001"
  }
}
```

说明：

- `taskId` 用于串联所有删除动作
- `aggregateType` / `aggregateId` 用于统一编排模型
- `payload` 可带必要的业务上下文，但不能塞入大对象快照

---

### 6.3 下游模块消费并清理自身数据

每个订阅该删除事件的模块，只处理自己的数据：

- Twin 模块：删除 Facility 与 ActorInstance 的 TwinMap / 映射
- Task 模块：删除该 Facility 对应任务、点位、巡检配置或做归档
- Alarm 模块：删除绑定规则、订阅关系或聚合索引
- 其他模块：删除本模块内部与该实体相关的数据

禁止消费方：

- 再去直接删其他模块表
- 依赖调用链式传播删除
- 因为“方便”而绕过边界直接做全局清理

---

### 6.4 处理完成后发布回执事件

成功回执：

```json
{
  "eventType": "facility.delete.step.succeeded",
  "taskId": "del-20260512-0001",
  "aggregateType": "facility",
  "aggregateId": 10086,
  "module": "twin",
  "occurredAt": "2026-05-12T12:00:03"
}
```

失败回执：

```json
{
  "eventType": "facility.delete.step.failed",
  "taskId": "del-20260512-0001",
  "aggregateType": "facility",
  "aggregateId": 10086,
  "module": "inspection",
  "occurredAt": "2026-05-12T12:00:05",
  "errorCode": "INSPECTION_DELETE_FAILED",
  "errorMessage": "inspection plan cleanup failed"
}
```

说明：

- 回执必须带 `taskId`
- 失败时必须带可追踪错误码和错误信息
- 回执事件只反映本模块处理结果

---

### 6.5 编排器汇总结果并更新主状态

删除编排器（可由主模块内部承担，也可独立为编排组件）负责：

- 跟踪每个删除任务的步骤状态
- 判断是否全部成功
- 决定是否重试失败步骤
- 决定是否进入人工处理

当全部步骤成功时：

1. 主实体改为 `DELETED`
2. 删除任务改为 `SUCCEEDED`
3. 对外返回删除完成状态

当存在失败时：

1. 主实体维持 `DELETING` 或改为 `DELETE_FAILED`
2. 删除任务改为 `PARTIAL_FAILED` 或 `FAILED`
3. 系统进入自动重试或人工重试流程

---

## 7. 删除失败处理规范

### 7.1 默认策略：挂起 + 重试

跨模块删除失败时，默认不做全局回滚，而是：

- 保持主实体为 `DELETING` 或 `DELETE_FAILED`
- 记录失败模块与失败原因
- 自动或人工触发重试
- 最终收敛到成功状态

这是本规范的默认处理策略。

---

### 7.2 不推荐策略：全局回滚

以下策略原则上不采用：

- Facility 删了又恢复
- Twin 已删再补回来
- Task 已删再回补
- 多模块统一做 Saga 式回滚

原因：

- 删除副作用通常不可逆
- 回滚实现复杂且容易产生更脏的数据
- 对工业系统而言，可恢复比“假全回滚”更重要

---

### 7.3 允许的失败后处理方式

失败后允许以下处理：

1. 自动重试
2. 人工重试
3. 标记失败并阻止继续业务使用
4. 导出失败明细供管理员处理

---

## 8. 幂等要求

所有删除消费者必须幂等。

### 8.1 幂等含义

同一个删除事件处理多次，结果必须一致，不得报错，不得造成重复副作用。

例如：

- twin mapping 本来就不存在，再删一次也应返回成功
- 任务已删过，再处理一次不能抛业务异常
- 索引已清除，再清除一次应视为成功

---

### 8.2 幂等实现建议

每个模块至少要做到以下之一：

1. 基于 `taskId + module + aggregateId` 做消费去重
2. 基于业务唯一约束判断数据是否已删
3. 删除时采用“存在则删，不存在即成功”的策略

---

## 9. Outbox 要求

### 9.1 必须使用本地事务 + Outbox

主模块在发起删除时，必须在同一事务中完成：

- 主实体状态更新
- 删除任务写入
- outbox 事件写入

之后再由异步投递器将 outbox 事件发送到消息总线。

---

### 9.2 为什么必须使用 Outbox

如果不采用 outbox，会出现以下问题：

- 数据库已改成 `DELETING`
- 但消息未成功发送
- 下游完全不知道要处理删除
- 系统进入不可观测脏状态

Outbox 用于解决：

# 本地事务成功，但消息未可靠投递

的问题。

---

## 10. 可观测性要求

删除任务必须可观测。

至少应支持查看：

- 主实体 ID
- 删除任务 ID
- 当前总状态
- 每个模块的处理状态
- 最近失败时间
- 失败次数
- 最近错误码
- 最近错误信息
- 是否允许人工重试

建议后续提供：

- 删除任务列表页
- 删除失败重试接口
- 失败告警通知
- 死信队列查看能力

---

## 11. 查询与前端展示要求

### 11.1 主列表查询

业务列表默认不展示 `DELETED` 数据。

对 `DELETING` 数据应按业务场景处理：

- 默认可隐藏
- 或以“删除中”状态显示
- 不允许继续编辑、绑定、关联新业务

---

### 11.2 详情页展示

若对象处于删除中或删除失败，应明确展示：

- 当前删除状态
- 失败模块
- 错误原因
- 是否可重试

禁止前端把“删除流程已受理”误展示为“删除成功”。

---

## 12. 删除前校验规范

删除前，主模块应先做本地业务规则校验。典型校验包括：

- 是否存在运行中的任务
- 是否存在禁止删除的巡检计划
- 是否存在必须人工解除的锁定状态
- 是否存在安全策略要求不能删除的数据

删除规则建议区分两类：

### 12.1 阻止删除型规则

满足即拒绝删除，例如：

- 存在运行中任务，不允许删除
- 存在未完成关键巡检，不允许删除

### 12.2 强制删除型规则

允许管理员确认后继续，例如：

- 删除并清理历史关联数据
- 删除并跳过非关键派生数据清理

注意：

是否允许“强制删除”是业务设计问题，不是基础设施默认行为。

---

## 13. 模块职责划分

### 13.1 主模块职责（以 Facility 为例）

Facility 模块负责：

- 接收删除请求
- 执行本地删除前校验
- 标记 `DELETING`
- 创建删除任务
- 写入 outbox 事件
- 汇总回执
- 更新最终状态
- 暴露删除状态查询与重试入口

---

### 13.2 下游模块职责

Twin、Task、Inspection、Alarm 等模块负责：

- 订阅删除请求事件
- 仅删除本模块边界内数据
- 处理成功/失败回执
- 支持幂等
- 支持重试

---

### 13.3 消息总线职责

消息总线只负责：

- 传递删除请求事件
- 传递步骤回执事件

消息总线不负责：

- 分布式事务一致性
- 跨模块回滚
- 业务编排判断

---

## 14. 事件命名规范

推荐统一命名：

### 14.1 请求事件

- `<aggregate>.delete.requested`

例如：

- `facility.delete.requested`
- `area.delete.requested`
- `site.delete.requested`

### 14.2 步骤结果事件

- `<aggregate>.delete.step.succeeded`
- `<aggregate>.delete.step.failed`

### 14.3 最终结果事件（可选）

- `<aggregate>.delete.completed`
- `<aggregate>.delete.failed`

说明：

- 是否发布最终结果事件可按系统需要决定
- 若要做审计中心、统一通知中心，建议补充最终结果事件

---

## 15. Facility 删除示例

以 Facility 删除为例，标准链路如下：

```text
用户删除 Facility
    ↓
Facility 模块本地校验
    ↓
Facility.status = DELETING
+ 创建 deletion_task
+ 写入 outbox event
    ↓
消息投递器发布 facility.delete.requested
    ↓
Twin 模块删除 twin mapping
Task 模块删除任务/点位/巡检配置
Alarm 模块删除规则绑定
    ↓
各模块分别回执 succeeded / failed
    ↓
Deletion Orchestrator 汇总状态
    ↓
全部成功 -> Facility.status = DELETED
存在失败 -> 保持 DELETING / DELETE_FAILED，并进入重试
```

---

## 16. 与后续模块迁移的关系

本规范是后续模块迁移时必须遵守的基础约束，尤其适用于：

- 旧 sinopec 项目中存在大量直接业务耦合的删除逻辑
- Task / Inspection / Point 等模块后续迁移到 Spring Cloud 后，需要重新定义边界
- Facility 作为主数据模块，未来会成为多个业务模块的上游实体

因此，后续迁移必须遵循：

1. 先梳理主实体与从属数据边界
2. 再定义删除请求事件与回执事件
3. 不允许临时通过 Mapper / Service 直连跨模块删表完成“快速迁移”

---

## 17. 禁止事项

以下做法在新架构中明确禁止：

1. 一个模块直接删除另一个模块的业务表
2. 以 RPC 同步串行调用多个模块并要求它们共同回滚
3. 主实体先物理删除，再补发消息要求下游清理
4. 删除失败后无状态记录、无错误明细、无重试能力
5. 同一个删除事件重复消费会抛错或产生重复副作用
6. 前端把“删除已受理”当成“删除已完成”展示

---

## 18. 推荐落地分级

### 18.1 第一阶段（当前必须做到）

- 主实体支持 `DELETING` / `DELETED` 状态
- 建立 deletion_task 表
- 建立 outbox_event 表
- 通过消息总线发布删除请求
- 下游模块返回成功/失败回执
- 支持人工重试
- 删除失败可观测

### 18.2 第二阶段（后续增强）

- 自动重试
- 指数退避
- 死信队列
- 删除任务管理页
- 最终结果事件中心化通知
- 批量删除编排

---

## 19. 结论

在新的微服务架构下，跨模块删除的核心不是“想办法模拟本地事务”，而是：

# 通过删除状态机、Outbox、幂等消费、步骤回执与重试收敛，实现可观测的最终一致性。

对于 Facility 及后续 Task / Inspection / Point 等模块迁移，必须统一遵守本规范，确保：

- 解耦边界清晰
- 删除行为可追踪
- 失败可恢复
- 架构可持续演进
